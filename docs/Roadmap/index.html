    Roadmap¶

    Where the app is, and what comes next. Every build of main has its own number (0.9.1, 0.9.2, …; Releasing); each heading below is the next minor version, and 1.0 is the stable release once the 0.x work has proven itself. Open problems live in Known Issues; what changed, and when, in the CHANGELOG.

    Each version says what it is for, then its items. An item is done when its Done when holds, not when the code is merged: a check that runs in CI, a number measured on a real machine, or a person doing it without help. Items marked ✓ are in the builds already; what they left open is listed under them.

    The two goals¶

    Since October 2026 the work is organised around two goals. 0.11 (real Docker in CI) is how both are proven; 0.12 and 0.13 are the goals themselves, and they run side by side.

    1. The same on every system. Every feature works the same way on macOS, Windows, and Linux (GNOME, KDE Plasma, and SteamOS), and CI proves it on each. Where something truly cannot be done on a system, Host says why, in place of a missing feature. Today's state is the table there, one row per feature.
    2. More apps in the catalog. Ten new apps and a second backup engine (0.13), each one held to the bar below.

    New apps no longer wait for 1.0. The earlier rule kept the catalog as it was until the stable release, so that 1.0 had less to prove. It is replaced by a bar each app passes on its own, so a new app adds its own proof instead of adding to what is unproven:

    • its compose service with an x-homelab block (category, description, what it replaces), and its own stack with a database when it needs one
    • its note under services/, generated with ./homelab docs and written by hand after the block
    • a row in Savings with a real, current price and its source (or a line under Not counted saying why not)
    • an end-to-end test against the fake docker: it installs, its data is backed up, and it gets its address
    • a place in 0.11's nightly run against real Docker, where it starts and answers on its own page
    • its image pinned the way the catalog already does (latest, which the nightly updates keep current, or an exact version with pin: saying why)
    • a line in the CHANGELOG

    A heavy app (Nextcloud, Frigate, Tdarr) is optional and in no starter or preset a newcomer picks by default.

    Where it stands (November 2026)¶

    A desktop app (macOS, Windows, Linux) and the homelab CLI that install, connect, back up, update, and watch over 72 self-hosted apps on one computer (the count in the README's generated table).

    • Setting up: Choose apps (starters, presets, every app by category, your own apps), a Setup checklist that runs the ready steps for you and leaves the sidebar once they are done, Home mode on the tailnet by default, and a domain with the proxy, AdGuard Home, Cloudflare Tunnel, and CrowdSec when wanted
    • Running: Status follows the container runtime live through Docker's own API (one engine, served by the background agent, which sends each change with the Status read after it and reads Status's cards once for every window and phone), says why an app failed to start or stopped answering, starts apps waiting for a drive, pauses heavy apps on battery, and gives background work a smaller CPU share
    • Healing: the watchdog every 15 minutes restarts an app that hangs, makes one whose container is gone again, rolls back an update that leaves an app unwell (with its data from before when it never came up well), and alerts through ntfy and an outside heartbeat
    • Backups: nightly database dumps and volume archives, Duplicati jobs off-site, a monthly restore test the app runs and times, moving the homelab to another machine, and rebuilding a lost one from the backups in one command (homelab rebuild), each app on the version that wrote its data (<APP>_DIGEST in .env)
    • Updates: the agent updates the apps nightly (each copied first; every app unless pinned, a database, or built here; held or paused from the app), the homelab files and the app itself found by themselves and put in place with one Update now, each app's release notes before it updates
    • The household: People with one sign-in (Pocket ID), Finances (the household's money, paycheck by paycheck, and net worth over time, typed in by hand and kept on this machine), a phone companion with Status, Backups, and Finances for the phones allowed them (in the browser, or the native iPhone and iPad app in apple-client/), kiosk mode for a wall screen, open-format export
    • The media libraries: Tidy Up files each download into its library (music, films, TV, books, audiobooks), cleans the music with beets, shrinks video with Tdarr, merges audiobooks, and tidies the books in Calibre, with Undo and the Trash behind every change (Tidy Up)
    • The app: a typed Preact frontend, native look per system (accent, Mica, translucent sidebar, high contrast, VoiceOver landmarks), Settings › Appearance (theme, accent, contrast, Islands, motion, transparency, tray icon colour), every screen fitting big text in a small window, and an AI that explains a log on this machine only
    • Safety: a threat review of the app's own code, govulncheck, gosec, and npm audit in CI, pinned Actions, and checksummed self-updates

    How it is tested today¶

    An audit in October 2026 (a tester's read of the code, CI, and Known Issues) found the code well covered by unit tests, and almost nothing proven against the real thing:

    • What CI runs: formatting, vet, and the Go tests (all pass; most packages 75–95% covered), the catalog and docs checks, every Compose file's syntax, the frontend's type check, cross-builds for macOS and Windows, and the security scans. All of it on Ubuntu.
    • What it does not: no container is ever started; the Go tests never run on macOS or Windows, only build for them; the Playwright click-through (make app-smoke) exists but is not in CI; and no test opens a homelab folder made by an older release.
    • Thin where a mistake costs most: single sign-on (sso, 11%), the Docker client (28%), the host checks (44%), self-update (49%), alerts (notify, 54%), the domain setup (56%); people and the recovery kit (recovery) have no tests.
    • A restore can come back on newer apps than the backup: 47 images follow :latest (Paperless, Vaultwarden, Ghostfolio, Docmost, Dawarich, Mealie, and others that change their own data on start). A backup records the data, not which version wrote it, and the image an update replaced is kept for a week on this machine only. A restore on a new machine starts the newest versions on older data. The PostgreSQL major versions are already pinned in .env; the apps above them are not. Fixed in October 2026: each backup records every app's image by its digest, .env keeps the version each app runs (<APP>_DIGEST), and a restore, a move, or a rebuild starts those versions.
    • The jobs' own logs grow forever: the agent appends to each job's file in scripts/logs (the watchdog every 15 minutes) and nothing trims them. The containers' logs are already capped (10 MB × 3).

    Since then, the Go tests run on macOS and Windows as well as Ubuntu, the click-through and its accessibility checks run on every pull request, the jobs' logs are trimmed, and every package has a coverage floor in CI, with the thin ones above now at 83–100% (0.11, ticked below). What is left of the list, 0.11 and the 1.0 bar below answer.

    0.11: proven against real Docker¶

    New in the October 2026 audit. Most of the "To verify" in Known Issues wait for a real runtime, not for the Mac: CI can start real containers, run the tests on each system, and click through the app. This version moves as much of that proof as it can from "try it on the machine" to "CI shows it every night", before more features are built on top.
