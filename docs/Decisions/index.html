    ADR-0001: A Mac as the only host¶

    Context: The homelab needs one always-on machine at home. Decision: Run everything on one Mac with Apple Silicon (a Mac mini, or a MacBook kept plugged in), kept awake by the homelab's awake job. Trade-offs: One machine is a single point of failure, and with FileVault nothing starts after a reboot until someone logs in. Apple Silicon is quiet and efficient, and native Jellyfin can use its media engine.

    ADR-0002: OrbStack as the container runtime¶

    Context: Docker on macOS always runs in a Linux VM. Decision: OrbStack, with Start at login enabled. Rationale: Lighter and faster than Docker Desktop, fast bind mounts, Rosetta for the few Intel-only images. The CLI uses the plain docker CLI, so Docker Desktop still works.

    ADR-0003: Cloudflare Tunnel for public access, through the proxy¶

    Context: Family members use some apps from outside the home without extra software. The router must not open ports. Decision: One remotely managed tunnel. Each public hostname points at http://nginx-proxy-manager:80, not at the app. Rationale: No inbound ports. Routing through the proxy means CrowdSec reads and blocks tunnel traffic exactly like LAN traffic, which removes the need for a separate edge bouncer and its Workers KV limits. The visitor's real address arrives in CF-Connecting-IP; proxy hosts trust X-Forwarded-Proto, so there is no redirect loop. Trade-offs: The proxy becomes a dependency of public access. The watchdog checks it every 15 minutes.

    ADR-0004: Custom Nginx Proxy Manager image with the CrowdSec bouncer¶

    Context: CrowdSec detects attacks but needs an enforcement point. Decision: Build dockerfiles/npm-crowdsec from jc21/nginx-proxy-manager plus CrowdSec's Lua bouncer (lua-cs-bouncer) and lua-resty-http, following CrowdSec's own OpenResty reference build. The bouncer configuration comes from environment variables at start. Consequences: Never update it by pulling the upstream image (that silently drops the bouncer). Left out of the nightly updates; ./homelab update nginx-proxy-manager rebuilds it. With no bouncer key the bouncer turns itself off instead of stopping the proxy.

    ADR-0005: No Cloudflare Access or WARP¶

    Status: Narrowed by ADR-0023 (November 2026): the phone companion's own hostname is behind Access with a service token, which the Homelab app sends itself. Every other app stays without Access, for the reasons below.

    Context: Cloudflare Access could gate the public apps behind a login. Decision: Do not use Access or WARP. Rationale: The public apps are used through native apps (Bitwarden, Immich, Subsonic players, Audiobookshelf) that talk to APIs and cannot complete an Access login. WARP would mean installing software on every family device. Mitigation: Strong unique passwords, 2FA where offered, CrowdSec, Cloudflare's managed rules.

    ADR-0006: Watchtower opt-in by label¶

    Status: Superseded by ADR-0020 (October 2026): Watchtower is gone; the agent runs the nightly updates, every app updates unless its x-homelab has a pin or it is a database or built locally.

    Decision: WATCHTOWER_LABEL_ENABLE=true; every service states com.centurylinklabs.watchtower.enable explicitly. Rationale: Updates happen where they are safe. The proxy (built locally), databases (major versions are pinned), and MoneyMatter (pinned build) are excluded and updated deliberately. The maintained nickfedor/watchtower fork is used because it negotiates the Docker API version.

    ADR-0007: Database dumps scheduled by launchd¶

    Context: Duplicati runs in a container and cannot run host commands before a job. Decision: ./homelab backup dumps every database at 03:30 into recovery-staging, and the Duplicati jobs run afterwards. Rationale: LaunchAgents run as the user, in the session where OrbStack lives, and the same command works by hand. The Linux and Windows profiles do the same with a systemd user unit and the user's Run key (all three now start one background agent, homelab agent, which runs the backup at 03:30).

    ADR-0008: compose files are the catalog; one CLI in Go¶

    Context: Describing apps in several places (scripts, JSON, docs) let them drift apart. Decision: Every app is a service with an x-homelab block in compose/<category>.yaml (included by compose.yaml) or stacks/*/compose.yaml. One Go binary (./homelab) installs, proxies, publishes, backs up, monitors, and documents from that metadata. Facts in the notes are generated from it. Rationale: A single source cannot drift. Go builds a single small binary with no runtime to install, starts instantly, and has testing built in.

    ADR-0009: One shared Docker network¶

    Decision: Every project joins the external homelab network. Web services are reached by service name; databases stay on their stack's private network. Rationale: No hairpin through host.docker.internal, no published ports needed for the proxy or the tunnel, and a database can never be reached from another stack. Service names must therefore be unique across stacks; homelab validate enforces it.

    ADR-0010: Native Jellyfin¶

    Decision: Jellyfin runs as the macOS app, not a container. Rationale: Containers on macOS have no access to Apple's hardware video encoder; the native app does. The CLI still proxies it (host.docker.internal:8096), and Duplicati backs up its data folder.

    ADR-0011: One .env for every project¶

    Decision: All projects read ~/Homelab/.env (the CLI passes --env-file). Rationale: One file to protect (mode 0600), one file in the Secrets backup job, and secrets generated in one place. COMPOSE_PROJECT_NAME must never be set in it, or it would override each stack's project name.

    ADR-0012: Home mode (no domain) is the default¶

    Context: A domain means a Cloudflare account, an API token, AdGuard on every device, and a certificate: the steps where a new household got stuck. Decision: HOMELAB_DOMAIN is empty in .env.example, so every new homelab, git clones included, starts in Home mode: Tailscale Serve gives each app https://homelab.<tailnet>.ts.net:<port>, and homelab tailnet setup reruns after every install. An existing .env keeps its domain; setting one later switches to the proxy, AdGuard, and the tunnel. Trade-offs: Each device needs Tailscale, nothing is published to the internet, and single sign-on with Pocket ID needs a domain.

    ADR-0013: The app updates itself from a numbered build of main¶

    Context: Downloading a build, dragging it to Applications, and clearing the download flag is too much to ask for every change. Decision: Every push to main that touches the app or the engine publishes the builds as a numbered release, the repository's Latest: VERSION with the patch raised by the commits since VERSION changed (v0.9.4-beta), so each build has a version people can read without a commit to bump it. Builds carry their version, commit, and repository (-X main.version, main.commit, main.repo); internal/selfupdate compares the commit with the newest build (the Latest release, or the newest vX.Y.0 on the stable channel), checks the download against GitHub's SHA-256 digest, replaces the app, and reopens it. See Releasing. Trade-offs: Until the builds are signed, the update trusts GitHub's release and digest. A release for every build fills the releases page; the stable channel takes only vX.Y.0. Since then (October 2026): on Windows the update unpacks the portable zip with Windows' own PowerShell (as an administrator only in Program Files) instead of running the installer, which SmartScreen and Smart App Control blocked as an unsigned program; an update that does not go in place says why, from update.log, instead of being offered again. Since then (November 2026, the owner's call): each release is one more than the newest, not the commits since VERSION changed: 0.17.0, 0.17.1, … 0.17.10, then 0.18.0 by itself (internal/tools/nextversion). Numbers like 0.16.41 said nothing a person could use; one number per release reads as a count of releases, and a new minor every eleven gives the stable channel something to move to. VERSION is the floor, raised by hand for a bigger step.

    ADR-0014: One engine, followed live through a local socket¶

    Context: The app, the menu bar item, and the phone each polled the container runtime every 10 to 60 seconds, so a stopped app showed late and each asked the runtime on its own. Decision: The engine follows docker events (internal/engine), gathering a burst into one change. The agent serves it on a socket only your account can open (/v1/status, /v1/events as Server-Sent Events); the app and the menu bar item follow it, and homelab serve passes the changes on to paired phones. Without the agent, each follows the runtime itself. Trade-offs: One more long-running process to keep healthy; a client falls back to its own follower, so nothing depends on it. Since then (0.15): the events, the containers, and the commands run in them go through the engine's own API (internal/dockerapi), with the docker CLI behind it; each change on /v1/events carries the Status read after it, and /v1/cards serves Status's cards once for every window and phone.

    ADR-0015: A typed Preact frontend, compiled and committed¶

    Context: The frontend was one 2,000-line script building the page by hand: no types against the Go side, and every live change rebuilt whole screens (losing focus and typed values). Decision: TypeScript checked against types generated from the methods the app binds, and Preact components per screen, compiled by esbuild into web/dist/app.js. The built file is committed, so go build needs no Node; CI fails while it is out of date. Preact rather than React or a framework with its own build: 10 KB, the same model, and no runtime beyond the bundle. Trade-offs: A contributor changing the frontend needs Node for make frontend; Go-only work does not.

    ADR-0016: The watchdog heals once, then leaves it to a person¶

    Context: Docker restarts a container that stops, not one that hangs (running, but unhealthy or not answering), and those stayed down until someone clicked Fix it. Decision: The watchdog restarts an app whose check failed on two runs in a row, at most once in 6 hours (AUTO_HEAL), and says so. An app updated in the last 6 hours is left to the rollback, which now also counts a page that stopped answering; a crash loop is left to Docker. Settings that changed under a running container are shown, not applied by themselves: recreating is the user's call (Fix it). Trade-offs: A restart can hide a slow leak until the next one; the alert on every restart keeps it visible.

    ADR-0017: CPU weights for background work, not throttling¶

    Context: Backups, photo indexing, and downloads could slow the apps people were using. Decision: Background services and the backup's own containers run with cpu_shares: 256 (a quarter of Docker's default). Weights only count while the CPU is busy, so idle machines still give background work all of it. Trade-offs: Only between containers: native apps such as Jellyfin are outside it. Watching load and changing limits on the fly was left out as more moving parts for the same result.

    ADR-0018: Not now: Docker Go SDK, tsnet, several machines¶

    Decision: Left out for now: the Docker Go SDK in place of the docker CLI (its JSON is already typed, and the CLI resolves each system's socket, context, and Windows pipe, which could not be tested here); Tailscale built into the binary with tsnet (Tailscale Serve already gives every app its address); several machines as one, and moving apps between them by power (a different product, for a household with one computer); GitOps (a homelab folder that is a git checkout already updates with homelab upgrade). Revisit when: the CLI's output stops being enough, or a household runs the homelab on more than one machine. Since then (0.15): the Docker part is being revisited, as the 0.10 timings on Windows asked: a small client of the engine's API of the homelab's own (not the SDK) reads the containers and runs commands in them, found as the CLI finds the socket, with the CLI as its fallback (DOCKER_API). A new ADR replaces this part once the timings on each machine are in (Roadmap).

    ADR-0019: Kopia as an optional second backup engine beside Duplicati¶

    Status: Accepted in October 2026, with the owner's answers below (Roadmap 0.13).

    Context: Duplicati is the only engine. One engine is one way to fail: its local database can need a repair before a restore, a restore of a large job is slow, and a bug or a corrupted destination loses every copy at once. The 3-2-1 rule (three copies, two kinds of storage, one off-site) is easier to meet with a second, independent copy.

    Proposal:

    • What it backs up: the same read-only sources as Duplicati (/source/appdata, /source/homelab-appdata, /source/stacks, /source/immich, /source/jellyfin, /source/calibre) and recovery-staging (the dumps and the secrets copy), as Kopia snapshots, one per source, so a restore can pick one app's folder.
    • Where: its own destination, never Duplicati's folder: KOPIA_REPOSITORY, a folder (a second drive, or a cloud drive's folder) or an S3-compatible bucket (Backblaze B2, Wasabi). The repository is encrypted with KOPIA_PASSWORD, kept with the recovery kit like DUPLICATI_SECRETS_PASSPHRASE.
    • How it runs: kopia/kopia (Docker Hub) as an optional app in compose/system.yaml, in server mode with its web page (admin only), on the same read-only mounts as Duplicati. Its own schedule runs after the nightly dumps (03:30), with cpu_shares like the other background work. Failures go to ntfy's duplicati-alerts topic through Kopia's webhook notifications, so one topic covers backups.
    • Restore test: homelab restore-test --auto gains --engine kopia. It picks the same sample of unchanged files from /source/appdata, restores them from the newest snapshot with kopia restore into recovery-staging/restore-test, and hashes them against the live files, exactly as for Duplicati. restore-test.json records the engine with each drill, and the 30-day reminder counts each engine. The nightly real-Docker run tests both.
    • The Backups screen: the off-site tile lists each engine with its last run and its last passed restore test; Test a restore asks which engine when both are set up. With Kopia not installed, nothing changes.
    • How someone chooses: Duplicati stays the default, set up by Setup. Kopia is in Choose apps › System as optional, described as "a second, independent copy somewhere else". Setup's backup step gains a line once it is installed: where its repository is, and whether its first snapshot and restore test passed.

    Trade-offs: two engines are two passwords, two destinations, and two schedules to explain; the disk is read twice each night; Kopia's web page is plainer than Duplicati's.

    Alternatives:

    • A second Duplicati job to another destination: no new engine, but the same software, so not independent of Duplicati's bugs or its database.
    • Restic with Backrest's web page instead of Kopia: similar design (content-addressed, encrypted, deduplicated); Kopia has its own web page and server mode in one image, Backrest is a separate project wrapping restic.
    • Kopia instead of Duplicati: fewer moving parts in the end, but it replaces a working, tested engine and every household's existing backups.

    Decision (the owner, October 2026): the safest and simplest choice for a household, each time.

    1. Beside Duplicati, not replacing it: Duplicati stays the default and the off-site copy; Kopia is the second, independent one.
    2. Kopia, not restic with Backrest: one app with its own web page, so fewer moving parts.
    3. Setup offers it as an optional step once it is installed, defaulting to a second drive; it never writes into Duplicati's destination.
    4. Yes: the nightly run tests a restore from both engines.

    ADR-0020: A rollback puts back the app's data with its image¶

    Status: Accepted in October 2026, with the owner's answers below (ISSUE-0022). Done after 0.14.0: the agent runs the nightly updates, and the owner chose to remove Watchtower altogether rather than keep it to pull and recreate, so no container holds Docker's socket to write to it.

    Context: A rollback starts the earlier image on today's data. An app whose newer version migrated its data (ntfy 2.11 after 2.34: "version 17 is higher than current version 13") then refuses to start. homelab update dumps databases first, but Watchtower's nightly updates are not preceded by anything, the rollback restores nothing, and files outside a dump (ntfy's message cache, SQLite apps' side files, settings folders) are not kept at all.

    Proposal:

    • A copy before every update. Watchtower stops updating by itself: the nightly updates are run by the agent as homelab update --all --nightly at the same hour, using Watchtower only to pull and recreate (its --run-once mode, for the apps that have a newer image). Before each app is updated, the homelab:
    • dumps its databases, as homelab update does today;
    • stops it and copies its own data: the bind-mounted folders inside the homelab folder and its named volumes (tarred, as archive: does), into recovery-staging/before-update/<app>/<time>/;
    • starts the update.
    • What is left out: folders outside the homelab folder (MEDIA_ROOT, IMMICH_UPLOAD_LOCATION, Jellyfin's data), and any folder over a size limit (UPDATE_COPY_LIMIT, 2 GB by default). Those apps' schemas live in their databases, which the dump covers. The update says which folders it did not copy.
    • The rollback (by hand, or the watchdog's after a failed update) stops the app; moves today's data aside to recovery-staging/rolled-back/<app>/<time>/ (never deleted by the rollback); puts the copy back; restores the dump into its database (PostgreSQL through pgexec, SQLite as a file); then starts the earlier image. It says what was put back and that changes made since the update are in the rolled-back folder.
    • Keeping copies: the newest copy per app, until the rollback window closes (a week, as for the earlier image); the backup's clean-up removes older ones.

    Trade-offs: each update stops the app for the copy (seconds for most, a minute for a large settings folder); disk for one copy per updated app; and anything written between the update and the rollback is set aside, not merged.

    Alternatives:

    • Keep Watchtower as it is and copy every app's data in the nightly backup before 4 AM: no change to how updates run, but a copy of every app every night, and up to a few hours of changes lost on rollback.
    • Restore only the dumps (no folder copies): smaller, but leaves ntfy's case, and every SQLite app's side files, unsolved.
    • Offer "restore the dump from before the update" as a separate step after a rollback: least work, but a person must know to do it, and the watchdog's automatic rollback still loops.

    Decision (the owner, October 2026): the safest and simplest choice for a household, each time.

    1. The agent runs the nightly updates (this proposal): only the job that updates knows the moment before, and it copies just the apps it is about to update.
    2. 2 GB per folder by default (UPDATE_COPY_LIMIT), and the databases are always dumped whatever their size; a folder left out is named in the update's result.
    3. The watchdog puts the data back by itself only when nothing new can have been written since the update: the app never came up healthy after it. Otherwise it rolls back the image, alerts, and offers Restore data as one step, so photos or documents added since the update are never set aside without a person choosing it.

    ADR-0021: Finances as a screen of the app, typed in by hand and kept on this machine¶

    Status: Accepted; built in October 2026 (#311, #323) and recorded afterwards from the code and the patch notes. The reasons below are what the design shows, not the owner's words: correct them here if they differ.

    Context: The household wanted to see, paycheck by paycheck, what checking holds once the bills are paid, which paycheck covers each bill, and net worth with the home's and car's equity. The catalog's budget apps (MoneyMatter, Actual Budget, Firefly III) keep what was spent; none reads pay and bills forward, and each is a separate app with its own sign-in, database, and update.

    Decision:

    • A screen of Homelab Wizard, not a catalog app. Finances is in the sidebar beside Status and Backups, drawn by the same frontend on the computer and the phone companion; internal/finance reads the plan forward (paydays moved before weekends and bank holidays, interest a day at a time, cards paying what is charged to them).
    • Typed in by hand, no bank connection. Nothing about the household's money leaves the machine, and no bank credentials or aggregator are involved.
    • One file in the homelab folder: data/finance.json, written 0600 and whole (a failed write leaves the last one), each balance kept by the day it was typed in for net worth over time. The nightly backup copies it with the household's other records into the encrypted Homelab Secrets job.
    • Phones by permission: off for every phone until picked (Sees Finances or Changes Finances, apart from Can make changes), only over an encrypted connection, never to a kiosk screen.
    • No lost saves: each read carries the file's version, and a save made after another device's is refused with the latest shown and the form kept.

    Trade-offs: balances go stale unless someone types them in (the heading says when they are a week old, and Update balances starts each at what is expected); no transaction history, categories, or imports, which stay the budget apps' job; and one more screen the app itself must keep working, outside the catalog's per-app proof (its checks are in the click-through and internal/finance's tests).

    ADR-0022: SQLite only for records that grow and are searched; small state stays in JSON¶

    Status: Accepted, November 2026, from the maintenance order (the owner's call). First used by the record of what was done (internal/history, November 2026), then the alerts the homelab sent (internal/history's alerts table: 90 days, at most 5,000, Nov 11).

    Context: The homelab keeps its own records as small JSON files in data/ (what is stopped, pinned, held, the watchdog's state, Setup's ticks), each changed whole under a lock beside it (internal/lockedfile, internal/applist) and copied by the nightly Secrets backup. That suits a record of a few kilobytes that is read whole. Two planned features are different: the Memory screen needs a day of samples taken every minute or so, and a record of what the homelab did needs months of entries that a screen filters and searches. As JSON, each would be read and rewritten whole on every change, and a search would read everything.

    Decision:

    • SQLite, in pure Go: modernc.org/sqlite, no cgo, so the same build works on a Mac, Windows, and Linux without a C toolchain, as every other part of the CLI does.
    • One database file in data/ (data/homelab.db), this account's alone (0600), opened in WAL mode so the app, the agent, and a phone's requests read while one writes. The nightly backup copies it through SQLite's own backup, as it already does for the apps' SQLite databases, never as a file copied mid-write.
    • Only for data that grows and is searched: the Memory screen's samples, the action record and the alert record. Each table keeps a limit (by age or by count) from the day it is added, so nothing in it only grows (see the maintenance order's Memory and growth).
    • Small state stays in JSON files: a record read whole and changed a few times a day keeps its file, its lock, and its whole write. Nothing moves into the database for being a record alone.

    Trade-offs: a dependency of some size (the pure-Go SQLite is a translation of SQLite's C, and grows the binary), a schema to migrate between versions, and a file that, unlike the JSON records, a person cannot read or fix in a text editor. In return the two growing records stay fast and bounded, and the rest of data/ stays as simple as it is.

    Alternatives: JSON lines files with rotation (simple, but every search reads them all, and a day of samples is rewritten to trim it); bbolt or another key-value store (pure Go too, but no queries, so each screen would grow its own index); the cgo SQLite driver (the original C, but a C toolchain on every build machine and harder cross-builds).

    ADR-0023: The iPhone app away from home: the companion through the tunnel, behind Access and sealed end to end¶

    Status: Accepted, November 2026 (the owner's call, Nov 9). The computer's side is built; the Setup step that makes the Access application and the iPhone's side follow.

    Context: The phone companion (homelab serve) answered only at home and on the tailnet, and refused anything with Cloudflare's headers, so on cellular the iPhone app showed nothing. The owner doesn't use Tailscale and won't add an app to every device; they use the Cloudflare tunnel, with Proton VPN's DNS. The companion holds Finances, so putting it on the internet as the other apps are (ADR-0005: their own sign-in, CrowdSec, Cloudflare's rules) is not enough.

    Decision: the companion gets one address through the tunnel, /api/tunnel, behind four locks, any one of which stops someone who got past the rest:

    1. Cloudflare Access with a service token on the companion's own hostname only. A request without the household's token is stopped at Cloudflare and never reaches the house. This narrows ADR-0005: the Homelab app sends the token itself (CF-Access-Client-Id and -Secret), so nobody completes a login, and no other app goes behind Access. The token reaches a phone only when it pairs at home, kept in its Keychain.
    2. Access's signed pass, checked by the companion (Cf-Access-Jwt-Assertion): RS256 by one of the team's keys (fetched from https://<team>.cloudflareaccess.com/cdn-cgi/access/certs, the team's name checked as one DNS label, cached an hour), for this application's audience, by the team's issuer, for the household's service token (common_name), and not expired. Anything else with Cloudflare's headers is refused, as before.
    3. The phone's own pairing: its device token, inside the sealed message, so a phone unpaired on the computer is cut off at once.
    4. Sealed end to end: at pairing, at home over an encrypted link, the phone and the computer agree a key (X25519, HKDF-SHA256 with the phone's ID), and every request and answer through the tunnel is sealed with it (AES-256-GCM; a request bound to its phone, an answer to its request). Cloudflare opens the tunnel's TLS, so without this it could read Finances; with it, it sees which phone, and nothing more. A request carries its time (within 2 minutes) and is taken once.

    Through the tunnel the phone only looks: a method that changes anything (Finances' edits included), the household's settings, a stream, pairing, and the frontend are never served there. Ten wrong attempts lock an address, or a phone, out for 10 minutes. A wall screen, and a phone paired over plain home Wi-Fi, get no key, so never go out.

    Trade-offs: the companion is reachable from the internet at all, where it wasn't; the locks are why that is acceptable, and each is tested (internal/companion/tunnel_test.go). The key lives in data/phones.json (0600) beside the hashed tokens, since a sealing key can't be kept as a hash; whoever can read that file can already read data/finance.json. Phones paired before this pair again once, at home. Cloudflare outages leave the phone with only what it last saw.

    Alternatives: Tailscale (encrypted, no Access needed, but the owner won't install it); Access with a person's login (the app can't complete one, as ADR-0005 says); Access alone without sealing (Cloudflare could read every answer); a VPN server at home (another app on every device, and a port to open).
