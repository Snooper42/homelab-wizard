    Automation¶

    Everything that runs on its own, and how to check it is alive. Setup › Scheduled jobs (Install the jobs) sets them up; you do not need to run any of them by hand.

    Scheduled jobs¶

    ./homelab schedule install installs one background job, com.homelab.agent (homelab agent), so the system's login items list one homelab entry. On a Mac it is a LaunchAgent in ~/Library/LaunchAgents, run as you in your login session, which is where OrbStack's engine lives; on Linux, a systemd user unit; on Windows, the homelab-agent value in your user's Run key, started through homelab-run.exe so no window opens. The agent starts the menu bar item too when it is set to start at login. Each part below runs as its own process, so one failing leaves the rest running, and writes scripts/logs/<part>.log. A log that reaches 5 MB is split before the next run: its older half replaces <part>.1.log and the newer half stays, so the watchdog's, written every 15 minutes, stays under 8 MB for as long as the homelab runs. homelab report reads the two as one. Installing removes the five separate jobs older versions installed.

    Part When Runs Purpose
    startup At login homelab up --apply --wait-media 15m Starts anything in the baseline that is not running; waits up to 15 minutes for the media drive first
    backup Daily 03:30, or as soon as the machine is awake after a missed night homelab backup --apply Dumps every database, archives listed volumes, notes each app's image by its digest, copies .env and the homelab's own records (data/*.json, data/people, data/sso, data/finance-receipts, data/finance-cards, data/members: the household, phones, Finances with its receipts and card pictures, and each member's own Finances) into recovery-staging, keeps the newest 7 of each; alerts duplicati-alerts on failure. Also measures the app folders and each person's photos (Status › What the apps keep), records the day's savings, sends the monthly restore-test and vault-export reminders and Finances' reminders (a bill due tomorrow, a paycheck under the cushion, a yearly renewal, stale balances; each can be turned off in Finances), asks GitHub for homelab updates (for the menu bar), and on Sundays sends the weekly summary (Monitoring)
    watchdog Every 15 minutes homelab watchdog --quiet Checks the runtime, every app, the database copies, the off-site jobs, the CrowdSec bouncer, free disk space, the apps' memory, and with a domain every public hostname (Monitoring); alerts tunnel-watchdog when something breaks or recovers, and keeps 7 days of counts for the % up this week badges. Keeps each updated app's previous image for a week, and rolls back an update that stays unwell
    backup-check Sundays from 07:00, or as soon as the machine is awake after homelab backup-check --quiet Duplicati's own Verify of each job that has run: a sample of its files at the destination downloaded and compared with the hashes it recorded. What it found is kept in data/backup-check.json; a damaged file makes the watchdog count that job as failing (and alert) and Backups say so beside it, until a check passes again. It runs beside the other parts, so the watchdog never waits for it
    awake Always (from login) homelab awake Keeps the machine from sleeping while it is plugged in, so the apps stay reachable; the screen still turns off. On a Mac this is caffeinate -s, which a laptop on battery ignores. KEEP_AWAKE=false (Settings, or unticking Keep this Mac/PC/computer awake while plugged in in the menu bar item's or tray icon's menu) lets it sleep as set; the job follows the setting within a minute, either way. homelab doctor warns when the machine would sleep with nothing keeping it up (it reads the sleep setting on a Mac, in GNOME, and on Windows). Whatever KEEP_AWAKE says, it also starts the apps the battery saver paused within a minute of the machine being plugged in (BATTERY_SAVER)
    serve Always (from login) homelab serve The phone companion on port 8099, home network and tailnet only (Phone companion); PHONE_COMPANION=false turns it off

    Check the agent with ./homelab schedule status (installed, last exit code). Each part's own log tells you what it did.

    Nightly updates (the background agent)¶

    Property Value
    Who The background agent, as homelab update --all --nightly; no container holds Docker's socket for it (Watchtower did this until 0.14)
    Schedule Daily at 4:00 AM (WATCHTOWER_SCHEDULE, named for Watchtower), after the 03:30 backup; not while homelab updates pause holds them (UPDATES_PAUSED)
    Scope Every app with a newer image, except those updated by hand (below) and held ones
    Cleanup The watchdog keeps each app's previous image as homelab-rollback/<app>:previous for a week (homelab rollback <app> goes back to it), then removes it; other old images go at once
    Before Each app with a newer image is stopped, its databases dumped and its folders and named volumes copied (recovery-staging/before-update, up to UPDATE_COPY_LIMIT a folder), then started on the new image: the same as homelab update <app>. The version it now runs goes into .env (<APP>_DIGEST), so a start, a move, or a rebuild brings that version back rather than a newer one
    After An app updated 20 minutes to 6 hours ago that is unhealthy, restarting over and over, or whose page does not answer on two checks in a row is rolled back by the watchdog, its updates held, and an alert sent to the watchtower topic (AUTO_ROLLBACK=false turns this off). If it was never well after the update, its data from just before goes back with the image (nothing new can have been written); if it was well for a while, today's data stays and the alert says homelab rollback <app> --data puts the copy back
    What is new homelab updates notes <app> lists the releases newer than the version it runs, with the start of each one's notes; homelab update prints one line per app, and the app's Update shows the notes before it goes ahead. They come from the GitHub project the image names (its org.opencontainers.image.source label, a ghcr.io name, or releases: in the app's x-homelab), kept 6 hours in data/releases.json
    Held homelab updates hold <app> and release <app> (UPDATES_HELD), or an app's page › Nightly updates; a stopped app can be held too
    Its own days homelab updates days <app> sun, or an app's page › Only on Sundays: the nightly run on another day leaves it out; every puts it back to each night. Kept in data/update-days.json ({"immich": ["sun"]}), not in .env
    Alerts ntfy topic watchtower (the name it had under Watchtower, so phones already subscribed keep getting them): what each night updated, and each rollback

    Who updates what¶

    Every container falls into one of three groups, generated from the compose files: rebuilt (a locally built image), by hand (an x-homelab pin saying why, or a database or cache), or nightly (every other app). Each service note's table says the same for its app.

    Nightly (69)¶

    The background agent runs ./homelab update --all at 4 AM (WATCHTOWER_SCHEDULE): for each app with a newer image it dumps its databases, copies its data, then pulls the image and recreates the container. Vaultwarden, Pocket ID, and CrowdSec (hold: 3) take a new image only once it has been out 3 days, counted from when the homelab first saw it, or once they have waited 14 days; ./homelab update <app> takes it at once.

    Duplicati (off-site backups)¶

    Duplicati runs the jobs below. Create the backup jobs on the Setup screen (or ./homelab duplicati setup) makes them through Duplicati's API:

    • AES-256 encryption with the passphrases in .env. They are generated if missing: DUPLICATI_SECRETS_PASSPHRASE for Homelab Secrets, and DUPLICATI_PASSPHRASE for the rest.
    • Zip compression and smart retention (a version a day for a week, a week for a month, a month for a year).
    • Each job writes into its own folder in BACKUP_DESTINATION.

    It leaves a job that already exists (by name) as it is. When a new job's folder already holds a backup (a rebuilt machine), it rebuilds the job's database from it (a repair) instead of a first run. It creates the photo, Jellyfin, books, and synced Files jobs only once their folder on this machine has something in it, and runs the small jobs once straight away. It first checks that Duplicati sees BACKUP_DESTINATION at /destination, and recreates Duplicati when it still has an older folder (after the setting changed). The sources are container paths. See Backups for the full mapping.

    Job Source Folder Schedule
    Homelab Photos /source/immich photos Daily 01:00
    Homelab Databases /staging/databases, /staging/volumes databases Daily 05:00 (after the 03:30 dumps)
    Homelab Secrets /staging/secrets secrets Daily 05:00
    Homelab AppData /source/appdata (without Duplicati's own folder) appdata Daily 05:30
    Homelab Stack Data /source/homelab-appdata stack-data Daily 05:30
    Homelab Infrastructure /source/stacks infrastructure Sundays 06:00
    Homelab Jellyfin /source/jellyfin (without its cache, transcodes, and logs) jellyfin Sundays 02:00
    Homelab Calibre /source/calibre calibre Sundays 03:00
    Homelab Files /source/sync (Syncthing's synced folders, SYNC_ROOT) files Daily 05:45

    ./homelab duplicati jobs lists them with their last and next run, as the app's Backups screen does.

    Failure alerts are set once for every job, as Duplicati default options: send-http-url is http://ntfy:80/duplicati-alerts?auth=<NTFY_PUBLISH_AUTH> and send-http-level is Warning,Error,Fatal. Set up the alert token (notify setup) and duplicati setup both set them; ntfy refuses anonymous posts, so they wait for the token. A job you make by hand gets them too.

    Alert topics (ntfy)¶

    Topic Published by
    watchtower The nightly updates and rollbacks (named for Watchtower, which sent them before)
    duplicati-alerts Duplicati job failures and homelab backup failures
    uptime-kuma Uptime Kuma monitors
    tunnel-watchdog homelab watchdog, and the Sunday weekly summary
    reminders The apps you point at it (Wallos renewals, Changedetection.io changes)

    ntfy refuses anonymous publishing. ./homelab notify setup gives the homelab user write-only access to exactly these topics and stores its token in .env; ./homelab notify test <topic> sends a test message with it. A new topic needs to be added to the list in internal/notify and notify setup run again, or its messages are refused.

    Principles¶

    • Everything previews first and needs --apply (or a yes in a terminal) to change anything.
    • Every job checks its own result: a dump must end with Postgres's completion marker, a copy must hash identically, and a URL must actually answer.
    • Alerts fire when something changes state, not on every check.
