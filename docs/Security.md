# Security

## Posture

| Area | Control |
|---|---|
| Inbound | No router ports. Public apps go through the Cloudflare Tunnel, which only connects outward |
| Edge | Cloudflare proxy with the free managed ruleset, Full (strict) TLS |
| Ingress | Every request, LAN or tunnel, passes Nginx Proxy Manager with the CrowdSec bouncer |
| Detection | CrowdSec reads the proxy's logs, bans attackers, pulls the community blocklist, and checks requests against virtual-patching rules (AppSec) |
| App ports | Bound to 127.0.0.1; only 53, 80, and 443 listen on the LAN |
| Containers | `no-new-privileges`, no container that can change Docker, read-only mounts where possible |
| Databases | Only reachable from their own stack's private network |
| Secrets | `.env` (0600, never committed) and Vaultwarden |
| Backups | Encrypted by Duplicati before they leave the Mac |
| Alerts | ntfy with deny-all access; only the alert topics are writable |

## Public apps

| App | Hostname | Authentication |
|---|---|---|
| Vaultwarden | passwords | Master password, 2FA required for every account |
| Immich | photos | Immich accounts |
| Paperless-ngx | docs | Paperless accounts, 2FA available |
| Navidrome | navidrome | Navidrome accounts |
| Feishin | music | Signs in to Navidrome |
| Audiobookshelf | audiobooks | Audiobookshelf accounts |
| Calibre-Web | books | Calibre-Web accounts (change the default admin first) |
| Komga | comics | Komga accounts |
| ntfy | ntfy | Deny-all; only the alert tokens and the phone's login (published once `notify setup` has made the token) |
| Nextcloud (optional) | cloud | Nextcloud accounts, 2FA available |

Any of these can be kept **home only** (`data/home-only.json`): an app's page › **Reach it away from home** off, or `homelab away off <app>`, takes it off the internet, removing only what the homelab put there (its tunnel rule, its service in the proxy, and the CNAME when it points at this tunnel; the household's own rules and records are left and named). A public app installed new starts home only until the switch is turned on; apps installed before stay as they were. The switch shows once the domain has the Cloudflare tunnel. The generated list of public hostnames is in [Inventory](<Inventory.md>). Everything else is LAN-only: its hostname is not in public DNS and not in the tunnel. Making an app public is one line (`public: true`) and must meet the [Contributing](<Contributing.md>) checklist first. Admin apps are never public: `homelab validate` (and CI) refuses `public: true` on an infrastructure app (the proxy, AdGuard, Duplicati, Dozzle, and the like) or one marked `admin: true` (Uptime Kuma). Publishing one would first need Cloudflare Access in front of it, signing in at Cloudflare before the page loads.

## CrowdSec

| Part | Detail |
|---|---|
| Engine | `crowdsec` container, collections `crowdsecurity/nginx-proxy-manager` and `crowdsecurity/appsec-virtual-patching` |
| Log source | `npm-logs` volume, read-only, via `config/crowdsec/acquis.yaml` |
| Bouncer | Lua bouncer inside the proxy image, stream mode, refreshed every 10 seconds |
| Bouncer key | `CROWDSEC_BOUNCER_KEY`, registered by the engine at start |
| Whitelist | Private addresses are never banned (CrowdSec's default) |
| AppSec | The bouncer sends each request to CrowdSec's AppSec listener (`crowdsec:7422`, `config/crowdsec/appsec.yaml`) and blocks those matching a virtual-patching rule: exploits of known vulnerabilities in common apps. Generic rules are not loaded, to keep normal traffic untouched |
| Failure mode | If CrowdSec is down, the proxy keeps serving from its last list, and requests skip AppSec (fails open) |

Test it with the ban runbook in [Runbooks](<Runbooks.md>).

Bans only hold while the proxy's bouncer pulls them, so `./homelab doctor` says when it last did, and the watchdog alerts when it stops (missing, revoked, or no pull for 5 minutes). The app's Status screen shows **Protection**: bans enforced or not, and what CrowdSec caught this week.

## Accounts and secrets

- Every password is 40 random characters, generated by Vaultwarden, unique per app.
- Turn on 2FA wherever an app offers it (Vaultwarden, Paperless, the personal Nginx Proxy Manager admin). Setup's **Two-step sign-in** step walks through Vaultwarden and the proxy.
- The Proxy Manager automation account (`NPM_API_EMAIL`) cannot use 2FA because the CLI signs in with it. Keep a separate personal admin with 2FA.
- Close Vaultwarden sign-ups (`VAULTWARDEN_SIGNUPS_ALLOWED=false`) once accounts exist.
- Secrets never go into git, notes, chats, command arguments, or logs. The CLI reads them from `.env` and sends them only to the service they belong to.
- Keep an offline copy of the Vaultwarden master password and `DUPLICATI_SECRETS_PASSPHRASE` (the Homelab Secrets job's passphrase, from `.env`). Without them, nothing can be restored.

## Docker socket

| Consumer | Access |
|---|---|
| Homarr, Dozzle (optional) | `docker-socket-proxy`, read-only: container list, logs, and engine info |
| Beszel agent (optional) | The socket mounted read-only: it runs on the host's network, where it cannot reach the socket proxy by name. A read-only mount does not limit what Docker's API allows, so treat it like the raw socket; pinned (`BESZEL_AGENT_VERSION`) and updated by hand, as the socket proxy is (N18) |
| Everything else | None |

## Updates

- The background agent updates the apps nightly, outside any container, copying each first; the proxy, databases, MoneyMatter, `docker-socket-proxy`, and the Beszel agent (both hold Docker's socket) are updated by hand.
- `./homelab update nginx-proxy-manager` rebuilds the proxy on the newest `NPM_VERSION` you set.
- macOS and OrbStack: install updates by hand, then log in straight away.

## The app's own code

The review above covers what can be reached from outside. This part covers the homelab's own code: the `homelab` CLI, the desktop app, and the frontend. `make security` runs three scanners, and CI runs it on every pull request (the *security* job):

| Scanner | What it looks for | Where |
|---|---|---|
| [govulncheck](https://go.dev/doc/security/vuln/) | Known vulnerabilities in the Go standard library and the Go packages the code uses, counted only when the code can reach the flawed function | The CLI for macOS, Linux, and Windows; the app for Linux and Windows (its Mac build needs a Mac to compile, so its Mac-only Wails code is not scanned) |
| [gosec](https://github.com/securego/gosec) | Risky patterns in the Go code: weak randomness, unsafe conversions, hard-coded secrets, unbounded decompression | Both Go modules |
| `npm audit` | Known vulnerabilities in the frontend's packages | Fails on any advisory in what is bundled into the app (Preact), and on high or critical ones in the build tools (esbuild, TypeScript) |

The builds use a current Go (`toolchain` in `go.mod` and `app/go.mod`), so fixes to Go itself reach the app. Until October 2026 the release builds were made with Go 1.25.0, which no longer gets security fixes.

**gosec rules left out**, because the homelab does these on purpose, as the person running it, with paths and commands it builds itself:

| Rule | What it flags | Why it is left out |
|---|---|---|
| G204, G702 | Running a program named by a variable | Running Docker, Compose, and the system's own tools is the homelab's job. Arguments go as a list. The few places that build a shell or PowerShell script from values are checked one by one in the [threat review](#threat-review-of-the-app-october-2026) |
| G304, G703 | Opening a file whose path is a variable | The paths are inside the homelab folder or the user's own settings. Unpacking an archive made elsewhere (a move file, a kit) is checked in the [threat review](#threat-review-of-the-app-october-2026) |
| G301, G302, G306 | Folders and files readable by other users (0755, 0644) | Logs, schedules, and generated pages are meant to be readable; `.env`, backups, and anything holding a secret are written 0600 |
| G104 | An error not checked | Low severity; the unchecked ones are best-effort clean-up (removing a temporary file, closing a window) |

The 14 other places gosec flagged were checked and marked in the code with `#nosec` and the reason (a percentage that cannot overflow, the names of settings mistaken for passwords, random numbers that only pick which backed-up files to test).

**When the security job turns red** without a change of yours, a new advisory was published. govulncheck names the package and the fixed version: update it (`go get <package>@<version>`, then `go mod tidy`; for Go itself, the `toolchain` line), or for npm, `npm update <package>`. If no fix exists yet, write it up in [Known Issues](<Known Issues.md>) with why it does or does not reach the homelab.

## Threat review of the app (October 2026)

Every way into the homelab's own code: what can reach it, what guards it, and what was found. Read against the code in October 2026 (0.6.0); the [review above](#review-october-2026) covers the apps and the network around them. Each finding is fixed in its own pull request, highest risk first, and ticked here when merged.

**Result: no high findings.** Six medium, five low, and the rest fine as they are.

### What was looked at

| Way in | Who can reach it | What guards it |
|---|---|---|
| Phone companion (`homelab serve`, port 8099) | Anything on the same network as the computer (home Wi-Fi, or a café's), and the tailnet | Private addresses only, nothing through Cloudflare; one-time 8-character codes, 10 wrong codes lock pairing for 10 minutes; device tokens stored hashed, compared in constant time; a fixed list of methods, read-only unless allowed, and allowed only to a phone paired over an encrypted link (M5); Finances only to a phone picked for them and only over an encrypted connection, never to a kiosk screen; Settings only over an encrypted connection, never to a kiosk screen, secrets never sent, and a phone changes only everyday settings (never a secret, nor what it connects through); strict CSP, no framing; tokens are sent as a header, never a cookie, so another website cannot act for a phone |
| Kiosk mode (`&kiosk` on the pairing link) | Anyone standing at the TV or wall screen | A screen paired in kiosk mode is read-only on the computer's side (M4), so showing the buttons again changes nothing |
| The engine's local socket | Programs running as you on this computer | Owner-only folder and socket; read-only (`/v1/status`, `/v1/status/last`, `/v1/events`, `/v1/cards`) |
| The desktop app's page | Only the app's own frontend, bundled into the app | Opens no port; outside text (release notes, logs, the model's answer) is shown as text, never as HTML; the only raw HTML is the app's own icons |
| Docker | Whatever can use Docker's socket | No container can change Docker (Watchtower, which could, is gone); the optional Beszel agent reads the socket mounted read-only; Homarr and Dozzle go through `docker-socket-proxy`, which allows no changes. On a Mac, Docker (OrbStack or Docker Desktop) can open the files in your home folder, so control of Docker is control of your files |
| Update downloads | Whoever controls the GitHub repository or its release workflow | HTTPS; the download checked against GitHub's SHA-256; opt-in install on quit. Unsigned until the Developer ID (1.0) |
| GitHub release notes | Each app's GitHub project, which writes its own notes | Shown as plain text; size-capped; cached 6 hours |
| Explain this (Ollama) | The model on this machine | Passwords and tokens taken out of the log first; the answer is shown as advice, nothing it says is run |
| Input from the page and the phone | The app's page; paired phones | `.env` values with line breaks are refused; app names are checked against the catalog before any command; phone actions are a fixed list |

### Findings

| # | Risk | Finding | Fix |
|---|---|---|---|
| M1 | Medium | **The release workflow uses actions by movable tags**, one of them third-party (`softprops/action-gh-release`) with write access to releases. A hijacked action could swap the builds that every copy's **Update** installs, and the checksum the app checks would come from the same release | **Fixed:** every action is pinned to a commit, and Dependabot proposes updates once a month; `TestWorkflowActionsArePinned` (November 2026) fails on any step that is not |
| M2 | Medium | **Unpacking a move file follows links**: a crafted move file can put a link to a folder outside the homelab, then write through it (into `~/Library/LaunchAgents`, say, which runs at login). Needs you to move in a file someone else made | **Fixed:** unpacked through `os.Root`, which cannot leave the folder, with a test of such a file |
| M3 | Medium | **Any paired device reads raw app logs**, a read-only phone or a kiosk TV included, and logs can hold passwords and tokens | **Fixed:** a log sent to a phone has `.env`'s secrets and anything shaped like a password or token taken out, as in a diagnostics report |
| M4 | Medium | **Kiosk mode is only a look**: a TV paired with *Can make changes* keeps that power, and `#kiosk=off` brings the buttons back | **Fixed:** a screen paired in kiosk mode is made read-only on the computer, whatever its code allowed |
| M5 | Medium | **The phone companion uses plain HTTP on the home network**: the pairing code and the device's token cross the Wi-Fi unencrypted, so someone on the same Wi-Fi who knows its password could copy a token. The tailnet link is encrypted (WireGuard) | **Fixed:** a phone paired over plain HTTP from the home network may only look, for good; changes need an encrypted link (Tailscale, the domain's https, or this computer), and a change sent over plain HTTP is refused |
| M6 | Medium | **The two containers that control Docker update themselves** from `:latest` every night (Watchtower, `docker-socket-proxy`). Whoever controls those images controls the computer | **Fixed:** both pinned and updated by hand after reading their notes, like the proxy and the databases; since then Watchtower is gone, and `docker-socket-proxy` stays pinned (`SOCKET_PROXY_VERSION`) |
| L1 | Low | `docker-socket-proxy` lets dashboards read each container's details, its settings from `.env` included, and Dozzle (optional) has no sign-in on the home network and tailnet | **Fixed:** Dozzle is kept to this computer: no tailnet or domain address (`local: true`), and `domain setup` removes the `logs.` proxy host an earlier setup made. The socket proxy itself has no published port; only the homelab's own containers reach it |
| L2 | Low | `HOMELAB_DOMAIN` reaches an administrator prompt unchecked: an elevated PowerShell script on Windows, a file path under `/etc/resolver` on the Mac. Only someone who can already edit `.env` could abuse it | **Fixed:** the domain and the address are checked before any prompt, and anything else is refused |
| L3 | Low | The app's **Open** opens any address its page asks for, not only web links. Needs another bug in the page first | **Fixed:** only `http`, `https`, and `mailto` addresses are opened |
| L4 | Low | An update without GitHub's checksum is installed unchecked (GitHub now gives one for every release file) | **Fixed:** a download without GitHub's checksum is refused |
| L5 | Low | On Linux, the Ollama note says to listen on `0.0.0.0`, which opens Ollama (no password) to the home network | **Fixed** with Docker Engine: Ollama listens on Docker's own address (`docker0`, `172.17.0.1`), which the containers reach and the home network does not, and the homelab's Explain, doctor, and Setup find it there. On SteamOS, Docker run as you reaches the computer only through its home-network address, so Ollama stays open to the home network there, as its note says |

Fine as they are: the engine's socket (yours only, read-only); another website pointing its name at this computer (DNS rebinding: without a code or a token it gets only the page); guessing a pairing code (31⁸ codes, 10 tries per 10 minutes, and only while one is waiting); the companion answering on a café's Wi-Fi (the page and pairing only); Explain with `OLLAMA_HOST` set to another computer (the log then leaves this one, with secrets taken out); the menu bar item's lock port (another program could keep it from starting, nothing more).

## Threat review (November 2026)

What was added since the [0.6.0 review](#threat-review-of-the-app-october-2026), read against the code by the security audit loop (`.claude/prompts/audit-loop.md`), one way in per round. Each finding is fixed in its own commit, with a test that fails without the fix, and ticked here when merged.

### Findings

| # | Risk | Finding | Fix |
|---|---|---|---|
| N1 | Low | **The phone companion trusts `X-Forwarded-Proto: https` from anyone** when it decides whether a request was encrypted. Checked against the M5 attacker (someone on the home Wi-Fi who copied a token): a phone paired over plain HTTP is made look-only and without Finances when it pairs (`MarkUnencrypted`), and `SetCanChange` and `SetFinances` refuse it later, so a copied token with a forged header gets nothing it did not have. A phone paired over an encrypted link keeps its token per address, so that token never crosses plain HTTP. The per-request check is a second layer, not the guard | **Fine as it is, now tested:** `TestAForgedHTTPSHeaderGivesACopiedTokenNothingMore`, which fails if pairing stops marking such a phone (checked by removing that step) |
| N3 | Low | **Two generated secrets were not taken out of reports and phones' logs**: `HOMEBOX_API_KEY_PEPPER` and `GHOSTFOLIO_ACCESS_TOKEN_SALT` are secret by their placeholder in `.env.example`, not by their name, and the redaction behind a diagnostics report and a log sent to a phone (M3) went by the name alone; their values are plain text that no token pattern catches. It needs an app's log or the report to print one | **Fixed:** what is secret is read as Settings reads it, by the name or by `.env.example` (`settings.SecretKeys`); `TestEverySecretIsRedacted` puts a value in every secret `.env.example` names and fails if any is left in a report or a phone's log (it named both before the fix) |
| N4 | Low | **The Windows update unpacks as an administrator from a file in your account's folder.** Between the checksum check and the approval prompt, a program already running as you could swap the zip, and it would be unpacked into Program Files with the administrator's approval. The script itself is fixed text with the paths as parameters, and the one command built from text (the elevated unpack) quotes both paths (`'` doubled) and is passed encoded | **Fine as it is:** it needs a program already running as you, which can already do anything you can; Windows does not hold its approval prompt to be a security boundary. Signed builds (1.0) let the app check the file again as the administrator |
| N5 | Low | **Set up the domain could move the household's own `*` record to this machine.** The home record (0.16.6) took over any `*.domain` A record at a private address, though the homelab never wrote one without its comment before: one a household made by hand for another machine (a NAS) was pointed here, and the watchdog would keep it here | **Fixed:** a record without the homelab's comment becomes the homelab's only when it already points at this machine; any other is left as it is and Set up the domain says so (`TestHomeRecord`, which moved a NAS's record before) |
| N6 | Low | **Explain took out only what looks like a token** before sending an app's log to the model, not the secrets in `.env` themselves; with `OLLAMA_HOST` on another computer, a secret an app printed plainly (a generated pepper looks like nothing) would leave this one, though the review above said secrets are taken out | **Fixed:** the log loses every secret value in `.env` first (`settings.Hide`, `settings.SecretValues`, which reports and phones' logs now share), then anything shaped like a token; `TestExplainSendsNoSecret` failed before (a password in the log reached the model's text) |
| N7 | — | **What a pull request from a fork can do in the workflows**: CI and Nightly run on `pull_request` (never `pull_request_target` or `workflow_run`), read-only and without secrets; Release runs only on pushes to main, tags, and by hand; no step puts a pull request's title, branch, or text into a script | **Fine as it is, now tested:** `TestWorkflowsGiveAPullRequestNothing` fails on either trigger, on a workflow without top-level permissions, or on such text in a step (checked by adding both to ci.yml) |
| N8 | — | **The agent's socket since 0.6.0** (`/v1/cards` added): it serves Status and its cards, the same as the window shows, read-only, to whoever can open it; it lives in your own runtime or cache folder, 0600 in a 0700 folder | **Fine as it is, now tested:** `TestTheSocketIsYoursAlone` fails if the socket or its folder is open to others (checked with 0666) |
| N9 | — | **The homelab's own records in `data/`** (Finances' plan, ledger, and receipts; people's welcome pages; sso; the paired phones): each written 0600, and off-site only inside the encrypted Secrets job (copied into its staging each night); Duplicati's other jobs read only `data/appdata` and `appdata`. `home-address.json` is 0644 and holds only this machine's address at home | **Fine as it is, now tested:** `TestNoOtherJobReadsTheRecords` fails if another job's source would take `data/` (checked by mounting `./data`) |
| N2 | Low | **Any paired device can make a diagnostics report** (`Report`, up to 3 minutes of work each), a look-only phone or a wall screen included, and several at once | **Fine as it is:** the report has every secret taken out (as a phone's logs, M3), it is how a household member sends one to their helper, and it changes nothing; a paired device is the household's |
| N10 | Low | **The record of apps stopped on purpose could lose a stop, or be read half-written** (`data/stopped.json`, 0.17). Three writers change it (the awake job each minute, `homelab stop`, and a phone's `StopUntil`), each by reading it, changing it, and writing it whole in place with no lock. The awake job held its copy through the seconds a `compose start` takes and saved it over a stop made meanwhile, and a reader in that moment could see an empty file: either way the watchdog, the battery saver, or a drive coming back started an app the household had stopped. It needs a paired phone that may make changes, or two things done on the computer at once | **Fixed:** changes go through `stopped.Update`, which holds a lock beside the record from reading to saving, and the awake job drops only entries no one changed meanwhile; the record is written to a new file and renamed in, 0600. `TestStartWhenDueKeepsAStopMadeMeanwhile`, `TestSaveReplacesTheRecordWhole`, and `TestUpdateLosesNoChange` each failed before |
| N11 | Medium | **Tidy Up's Undo moved whatever its trash log named** (`data/media-trash.jsonl`, `homelab media restore`, 0.17). Each line says where a thing was (`from`) and where it went (`to`), and Undo moved `to` back to `from` whenever `to` was there and `from` was not, wherever either was. A homelab moved in from a file someone else made brings its `data/` (this log, and the run Undo offers), and the move file can bring the file too: one press of **Undo** then put it among the login items (`~/Library/LaunchAgents`, `~/.config/autostart`), which run at the next login, as M2 did through links | **Fixed:** Undo moves a thing back only from where Tidy Up puts what it throws away: directly in the Trash of its old place's drive, or that drive's `.tidy-trash` dated folder on Windows (`trashed_from`); anything else is named and left. `test_a_crafted_log_moves_nothing_that_is_not_in_the_trash` failed before (it planted two) |
| N12 | Low | **Tidy Up's screen could hand its jobs any argument** (`TidyRun`'s `args`, 0.17): passed to `homelab media` as they came, so a page with a bug in it could add `--library` to point a job at any folder (sorting, renaming, and putting in the Trash what it found there), or name files for `file`. The screen itself sends only `--apply`, `--check`, `--skip` with book ids, and Undo's run. It needs another bug in the page first, as L3 did | **Fixed:** `tidyArgs` takes only those, and Undo exactly one run (`tidyScreenArgs`); anything else is refused before a command runs. `TestTidyArgsTakesOnlyWhatTheScreenSends` failed before (all 9 such arguments went through) |
| N13 | Low | **Changes from different places ran at once.** The app, `homelab serve` for a phone, and the agent's nightly backup and update each kept only their own "one at a time", so an Update all in the app, a phone's Restart, and the nightly backup stopping a database could all reach Docker Compose together; and the watchdog could restart an app an update had just taken down. ## Review: the phone companion through the tunnel (November 2026)

The owner asked for the iPhone app away from home without Tailscale (ADR-0023). This puts one address of the companion, which holds Finances, on the internet, so it was reviewed before it merged, against someone on the internet, Cloudflare itself, someone who stole a phone, and someone who copied a pass or a message.

**What is exposed:** `https://<the companion's hostname>/api/tunnel`, POST only, behind Cloudflare Access. Nothing else of the companion answers through the tunnel: the page, pairing, `/api/call`, `/api/me`, `/api/events` and the calendar are refused there before anything is read (`TestTheTunnel`).

| Who | What they try | What stops them | Test |
|---|---|---|---|
| Anyone on the internet | Reach the companion | Access stops a request without the household's service token at Cloudflare. If Access were turned off or the hostname set up by mistake, the companion still needs Access's signed pass, and its sealed message | `TestTheTunnelNeedsAccesssPass` |
| Anyone with a pass of their own | Another Cloudflare team's pass, another application's, a person's login, or one signed by a key that isn't the team's | The pass is checked against the team's own keys, the application's audience, the team's issuer, the household's service token (`common_name`), and its expiry | `TestTheTunnelNeedsAccesssPass` |
| Cloudflare, or whoever reads the tunnel | Read Finances, or change a request | Every request and answer is sealed end to end (AES-256-GCM) with a key agreed at home (X25519); Cloudflare sees which phone and the size, nothing more. A changed box doesn't open | `TestTheTunnel` (answers don't show their contents), `TestTheTunnelNeedsThePhone` |
| Someone who copied a sealed request | Send it again | A request carries its time (2 minutes either way) and each is taken once | `TestTheTunnelNeedsThePhone` |
| Someone with the service token, or a valid pass | Ask without the phone | The message must be sealed with that phone's key and carry its device token | `TestTheTunnelNeedsThePhone` |
| Whoever has a lost or stolen phone | Keep using it | Unpair on the computer cuts it off at once (its key and token go); Face ID on the phone, as at home; only looking, never a change | `TestTheTunnelNeedsThePhone` |
| Someone guessing | Many tries | 10 wrong attempts lock the address, or the phone, out for 10 minutes | `TestTheTunnelLocksOutAfterWrongAttempts` |
| Someone on the home Wi-Fi | Catch the key at pairing | The key is agreed (X25519), never sent; and only for a pairing over an encrypted link, never plain Wi-Fi, never a wall screen | `TestTheTunnelKeyIsGivenOnlyWhereItIsSafe` |

**What a phone may do through the tunnel:** look only. A method that changes anything (`Method.Change`), anything at the Finances edit level (N31), the household's settings (`Private`), streams, and anything a phone may not do at home are refused, sealed, with words saying it waits until home. Finances go only to a phone already allowed to see them.

**Left as it is:**
- Cloudflare learns that a phone is in use, when, and how much it sends, but not what.
- The sealing key is in `data/phones.json` (0600), since it can't be kept as a hash. Whoever can read that file can already read `data/finance.json` beside it.
- The team's keys are fetched from Cloudflare; the address is made from a team name checked as one DNS label, so it can't be pointed elsewhere.
- Lockouts are kept in memory: restarting `homelab serve` clears them. Cloudflare's own rate limits stand in front.

## Review: the record of what was done (November 2026)

`internal/history` keeps what was done in `data/homelab.db`, the homelab's first SQLite file (ADR-0022).

- **What it stores:** one line per thing done (*Restarted Immich*, *Changed settings: QUIET_HOURS*, *Changed Finances' transactions*), its kind, the app's id, when, and who did it: *this computer*, a phone by the name it paired with, *the watchdog*, or *the nightly update*. Never a setting's value, a secret, or an amount of money: settings are named only, and Finances says only what kind of thing changed. A household member's own Finances are never recorded. Lines are cut at 500 characters and kept to one line without control characters.
- **Who can read it:** this account (the file and its `-wal` and `-shm` files are 0600, made so before SQLite opens them); `homelab history`; the desktop app (`History`); and the owner's paired phones through the companion's look-only `History` call, every line through `phoneLog`'s redaction of `.env`'s secrets and anything shaped like a token. A member's phone and a wall screen can't call it (N34).
- **How long:** 90 days, and at most 20,000 entries (the newest), trimmed on every write.
- **Backups:** the nightly Secrets backup takes a copy made through SQLite (`VACUUM INTO`), encrypted with `.env` and the other records, never the file copied mid-write.
- **Who it names:** a phone's own name, as its owner gave it at pairing, and reached from the companion's verified caller (`companion.Caller`), passed to the command it runs (`HOMELAB_ACTOR`). A terminal user can set that variable by hand, which only changes the line they write about themselves.

## Independent review of #544 to #560 (November 2026)

Everything merged from #544 to #560 was read again by a session that wrote none of it. What was found is N31 to N34 above; what was checked and holds:

- **Home only can't remove the household's own work (#559):** `Unpublish` drops only a tunnel rule for the app's exact hostname that sends it to the proxy (as Publish writes it), and a CNAME only when it points at this tunnel; a rule for another service, a wildcard, the catch-all, and a record of another kind or pointing elsewhere are left and named (`TestUnpublish`, `TestAwayOffKeepsAnAppHomeOnly`).
- **Who can publish an app (#559, #560):** `SetAppSetting` is `Change`, so a phone that only looks is refused, a member's phone is refused (not `Member`), a wall screen has no changes, and the tunnel refuses it; on the iPhone it asks for Face ID first. The app id must be in the catalog and the hostname is made from the catalog's subdomain, so nothing a phone sends reaches Cloudflare's API but a known app; DNS names and record ids are escaped.
- **The tunnel's locks (#544 to #548):** Access's pass is checked for RS256, the team's own keys (2048-bit or more, fetched only from `<team>.cloudflareaccess.com`), audience, issuer, the service token and expiry; a sealed request is AES-256-GCM bound to its phone, its time within 2 minutes, each taken once (kept 4 minutes, past the window); an answer is bound to its request; wrong attempts lock out. A header that claims Cloudflare only makes a request stricter.
- **Links and alert buttons (#549, #550):** `homelab://` carries no secret and changes nothing by itself: an action waits in a dialog for a tap, then goes through the button's own path (Face ID, and Stop asks again), only on a phone allowed changes. The computer sends only links it built from a valid app id and a known action.
- **`/api/me`'s computer info (#551 to #553):** only to a paired device; the version, the call names and the features, the same for every device and already in the public source.
- **The \*arr apps resting (#554):** it stops nothing while a job holds the lock, each stop is noted in `data/stopped.json` so the watchdog leaves it, and the apps' keys are read from their own config and sent only to them, at home.
- **The record of what was done (#555):** every query is parameterised (a search's `%` and `_` escaped); settings are named, never their values; Finances only by kind, never a member's; the files are 0600.
- **Databases (backlog item 60):** every database in the catalog (19 today: Postgres, Valkey, Redis, Meilisearch) is on its own stack's network, none on `homelab`; `TestDatabasesStayOffTheSharedNetwork` keeps it so.
- **CrowdSec's API on the shared network (backlog item 59):** any app on `homelab` reaches `crowdsec:8080` and the AppSec listener on 7422, but reading decisions and asking AppSec both need the bouncer key, and adding or removing a ban needs a machine login: a new machine stays pending until `cscli machines validate` inside the container, as the homelab never turns on auto-registration. An app could only knock.
- **A hand-kept catch-all in the tunnel (backlog item 65):** covered by N33: when such a rule and a wildcard record would carry a home-only app, Set up the domain and `homelab away off` say so.

## Incident response

1. Look: `cscli alerts list`, the proxy logs, the app's logs.
2. Contain: stop the app (`./homelab stop <app>`), or remove its public hostname by setting `public: false` and rerunning `./homelab domain setup` (the tunnel route stays until removed in Cloudflare; delete it there too).
3. Ban by hand if needed: `./homelab compose crowdsec exec crowdsec cscli decisions add --ip <address> --duration 24h`.
4. Rotate any secret that might have leaked (the app, `.env`, Vaultwarden).
5. Write it up in [Known Issues](<Known Issues.md>).
