    Architecture¶

    One computer runs everything: containers in its container runtime (OrbStack on a Mac, Docker Engine on Linux, Docker Desktop on Windows; Host), plus two native apps (Jellyfin, and the phone companion that homelab serve runs). The drawings below use the Mac. Apps are split into Compose projects that share one Docker network.

    Every new homelab starts in Home mode (HOMELAB_DOMAIN empty): Tailscale gives each app an https address on the tailnet, and nothing needs a domain, Cloudflare, or the proxy. With a domain, all traffic, from the LAN or from the internet, enters through Nginx Proxy Manager, where CrowdSec blocks known attackers. The topology below is that domain setup.

    Nothing listens on the router: the tunnel is opened from the Mac outwards, and every request, from home or from the internet, passes the same proxy and the same CrowdSec check before it reaches an app.

    Traffic paths¶

    Home mode: device in the tailnet → https://<TAILSCALE_HOST>:<port> → Tailscale Serve in the tailscale container → app by service name. With TAILNET_ADMIN_APPS=false, the admin apps are left out and open on this machine only.

    LAN: device → AdGuard Home (*.example.com → 192.168.1.10) → Nginx Proxy Manager (TLS, CrowdSec check) → app by service name on the homelab network.

    Internet: visitor → Cloudflare edge (TLS, managed rules) → Cloudflare Tunnel → http://nginx-proxy-manager:80 → CrowdSec check, using the visitor's address from CF-Connecting-IP → app.

    Native apps: Nginx Proxy Manager → host.docker.internal:8096 → Jellyfin on the Mac.

    Only apps marked public: true get a public hostname in the tunnel. Every other hostname exists only in AdGuard, so it never resolves outside the home network.

    Single-container apps are grouped by category, one project each (compose.yaml holds the categories, presets, and native apps). Multi-container apps get their own project so they can be stopped, updated, or restored without touching the rest. Inside a stack, databases stay on the stack's private network; only the web-facing service joins homelab.

    The desktop app and the phone companion read through the engine directly (catalog, status, plans, installs) and run the CLI for actions, so a button and a Terminal command always do the same thing. The engine reads the containers, their events, what they use, and the runtime's info from the runtime's own API over its socket (internal/dockerapi; Docker Desktop's named pipe on Windows), one request on a kept connection, with the docker CLI answering whenever the API fails (DOCKER_API=off keeps the CLI; homelab doctor says which is in use); starting and updating apps is still docker compose. It also follows the container runtime (internal/engine, from those events): a container that starts, stops, or changes health reaches the app's Status and the menu bar item at once, gathered into one change per burst, instead of at the next poll. The agent serves it on a socket only your account can open ($XDG_RUNTIME_DIR/homelab-wizard/engine.sock on Linux, the cache folder elsewhere): GET /v1/hello, /v1/status (?now without waiting for the apps' pages; requests that arrive together share one reading of the runtime), /v1/status/last (the last reading and when it was taken, which a window that opens draws at once, marked with its age, while it reads a fresh one), /v1/events (each change, as Server-Sent Events, carrying the Status read after it, so a window draws it without asking), and /v1/cards (the cards beside Status, read once for every window and phone, each sent as it is read; internal/board), so the app, the menu bar item, and the phone companion follow one engine (homelab serve passes the changes on to paired phones at /api/events); without the agent, each follows the runtime itself and looks for the agent again each minute. The phone answers only on the home network and the tailnet, and only to phones paired with a one-time code. The compose files are the single source: the CLI, the app, the generated docs, and the savings figures all read their x-homelab blocks. Scripts read the CLI's --json output, one {"schema": 1, "type": ..., "data": ...} object per line; internal/api/testdata/contract.json holds the fields a test keeps stable (Commands).

    The frontend is TypeScript (web/src): each screen's module (web/src/screens) reads its data through the engine into a store (store.ts), runs the commands, and mounts Preact components per screen and card (web/src/status, backups, choose, setup, settings, finances, page, updates, job, sheets, and the shared blocks in parts), which draw and keep what is typed; app.ts only chooses the screen, answers the keyboard, and starts the app. esbuild compiles it into web/dist/app.js, committed so the Go builds need no Node; the types it is checked against are generated from the methods the app binds (web/types/backend.d.ts). The desktop app and the phone companion load the same files.

    Watching and healing¶

    Each layer catches what the one before it cannot:

    What goes wrong Noticed by Put right by
    A container stops or crashes Docker's events, at once Docker's restart policy
    A container runs but its page does not answer, or its health check fails Status asks each app's address as it loads (internal/api); the watchdog every 15 minutes The watchdog restarts it after two failed checks in a row, once in 6 hours at most (AUTO_HEAL); Fix it restarts, then recreates
    An update leaves an app unwell (unhealthy, restarting, or not answering) The watchdog, 20 minutes to 6 hours after the update Rolled back to the image it ran before, its updates held (AUTO_ROLLBACK)
    .env or a compose file changed, but the container still runs the old settings Compose's configuration hash on each container against what Compose would make now (api.Changed) Fix it (or up) recreates it
    Backups, indexing, or downloads crowd out the apps in use CPU weights: background containers get a quarter of the default share while the CPU is busy

    Before an update, the app reads the GitHub releases of the project each image comes from (internal/releases: from releases: in x-homelab, the image's source label, or a ghcr.io name), newer than the version it runs, cached for 6 hours. Explain this sends an app's last lines, with passwords and tokens taken out, to the Ollama on this machine (internal/explain); nothing goes to a service outside the house.

    The desktop app updates itself (internal/selfupdate, app/updates.go): it looks every 15 minutes and when its window comes forward, downloads a newer build ahead, and Update now (the line at the top of the window) moves the homelab files forward (homelab upgrade), then downloads the newest app build, the repository's Latest release (each build of main is one, v0.9.4-beta and on; the newest vX.Y.0 with UPDATE_CHANNEL=stable), checks its SHA-256 checksum, and replaces the running app: on a Mac the .app bundle, on Windows the files put in place by Windows' own PowerShell (as an administrator only when the app is in Program Files), on Linux the AppImage by a rename or the package through pkexec. Each attempt's steps go in update.log in the user's cache folder, and a build that did not go in place says why when the app opens again.

    A night in the homelab¶

    When What Notes
    Every 15 minutes Watchdog Checks the container runtime, the proxy, the tunnel, every app's health and page, the database dumps' age, Duplicati's jobs, and the public names; alerts on the second failure in a row, restarts an app that hangs (once in 6 hours), and pings the outside heartbeat
    01:00 Duplicati: Photos Immich's library, encrypted, into Proton Drive
    03:30 homelab backup Dumps every database (consistent SQLite copies too), archives listed volumes, copies .env and the homelab's own records in data/ (the household, phones, Finances), and notes each app's image digest; so every database has a dump from just before the updates. It also measures photos per person and each app folder (data/storage.json), asks GitHub once a day for homelab updates, and on Sundays sends the weekly summary
    04:00 The agent's nightly updates For each app with a newer image: stops it, dumps its databases and copies its data, then starts the new image and writes the version it now runs to .env (<APP>_DIGEST, which a start, a move, and a rebuild bring back); reports to ntfy. The watchdog then keeps each app's previous image for a week and rolls back an app that stays unwell or stops answering
    05:00 Duplicati: Databases, Secrets The fresh dumps and .env, encrypted, into Proton Drive
    05:30 Duplicati: AppData, Stack Data Every app's settings folders
    Weekly Duplicati: Infrastructure, Jellyfin, Calibre The stacks folder and the larger libraries

    Baseline and slot-in apps¶

    • Baseline: everything without a profile. ./homelab up starts it, and the startup job runs it after every login.
    • Optional: services with profiles: [optional] are defined and documented but stay off until ./homelab install <app>.
    • New services: add a block to the category's file in compose/ (or a folder under stacks/ for an app with its own database) with an x-homelab block. The CLI then installs, proxies, publishes, documents, and monitors it like the rest. See Contributing.

    Security boundaries¶

    Layer Control
    No open router ports Cloudflare Tunnel and Tailscale connect outward
    Tailnet (Home mode) Only devices signed in to your tailnet reach the apps; TAILNET_ADMIN_APPS=false keeps the admin apps on this machine only
    Edge Cloudflare's free managed ruleset
    Ingress (LAN and tunnel) Nginx Proxy Manager with the CrowdSec bouncer
    Detection CrowdSec reads every proxy log and pulls the community blocklist
    App ports Bound to 127.0.0.1 on the Mac; other devices go through the proxy
    Accounts 40-character passwords in Vaultwarden, 2FA where offered
    Secrets .env (mode 0600) and Vaultwarden
    What the app asks outside GitHub, for homelab and app updates and apps' release notes (project names only); the Ollama for Explain this is on this machine

    See Security for details and Decisions for why.

    Known architectural limits¶

    Limit Effect
    Single host If the Mac is off or asleep, everything is down. homelab move out and move in carry it to a new machine, and homelab rebuild brings it back from the backups when the machine is lost. The awake job keeps it from sleeping while plugged in (KEEP_AWAKE).
    FileVault After a restart nothing runs until someone logs in (OrbStack and the jobs run in the login session).
    A router that cannot push DNS Each device's DNS is set to 192.168.1.10 by hand, or Tailscale's DNS setting points every Tailscale device at AdGuard (@adblock).
    No VLANs Everything shares the home LAN.
