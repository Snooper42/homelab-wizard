# Testing

A script for testing a new build on the Mac, in order. Each step says what to do and what you should see. When something does not match, check [Troubleshooting](<Troubleshooting.md>), then stop there and make a report:

```sh
./homelab report
```

It writes `scripts/logs/report-<date>.txt` with doctor, status, the setup checklist, the jobs, Duplicati's jobs, the weekly summary, the updates waiting, which settings are set, and the logs of anything unwell. Passwords, tokens, and anything shaped like one are replaced with `[redacted …]`. Read it through, then share the file or paste it. Never paste `.env` itself, a token, or a password. The app has the same thing as Settings › This Mac › **Make a diagnostics report**.

Type each command as shown, one line at a time. In zsh a `#` on the line is not a comment, so there are none here.

## 1. Bring the Mac up to date

If you tested an earlier build, read [Upgrading](<Upgrading.md>) first: it lists what changed and the few steps it asks of you.

```sh
cd ~/Homelab
./homelab upgrade
./homelab version
./homelab doctor
```

- `upgrade` lists what changed and what is new, asks, moves the folder forward, and runs `up` afterwards. **Update now** in the app does the same, and updates the app too. (A clone from before `upgrade` existed: `git checkout main` and `git pull` once instead.)
- `version` prints the repository's version; the first run after an update builds the CLI ("Building the homelab CLI...").
- `doctor` ends without ✗ lines. Expected ! warnings: a VPN if one is on, and settings you have not filled in yet.
- If OrbStack still lists a `homelab_core` project, `upgrade` moves the containers into their category projects (`homelab migrate`, a backup first). OrbStack then lists them grouped as homelab_network, homelab_security, homelab_system, homelab_media, and so on, every app keeps its data and settings, and `doctor` no longer mentions `homelab_core`.
- With `brew install smartmontools` done, `doctor` lists each drive under **Drive health** as passed (the Mac's own SSD at least; a USB drive may say it gives no report).

## 2. The desktop app

1. The first time only, in Terminal (Linux too; on Windows, `irm https://raw.githubusercontent.com/Snooper42/homelab-wizard/main/install.ps1 | iex` in PowerShell):

   ```sh
   curl -fsSL https://raw.githubusercontent.com/Snooper42/homelab-wizard/main/install.sh | sh
   ```

   It installs the newest build from GitHub › Releases › **Latest** after checking its checksum, and opens it. Once the app is installed, it updates itself (**Update now** on the line at the top), so skip to step 3.
2. From a browser instead: download `Homelab-Wizard-macOS.dmg`, drag **Homelab Wizard** to Applications, then clear the download flag once (the build is not signed):

   ```sh
   xattr -dr com.apple.quarantine "/Applications/Homelab Wizard.app"
   ```

## 4. The jobs

```sh
./homelab watchdog
./homelab backup --apply
./homelab schedule status
```

- Stop one baseline app (`./homelab stop navidrome`), run `./homelab watchdog` twice: the second run shows *Homelab: something is down* in Notification Center as well as on the phone. `./homelab start navidrome` and the next run shows *recovered*.
- A restart that keeps failing: `./homelab custom add crashy --image alpine:3.20 --install --apply` (it exits at once, so Docker keeps restarting it). Run `./homelab watchdog`, wait 3 minutes (Docker waits longer between each restart, up to a minute), and run it again: the second run says *stopped crashy: Docker restarted it … times in an hour*, the phone gets *Homelab: stopped an app that kept restarting*, and Status's crashy row says *Stopped: it restarted … times in an hour* with a red dot. Another `./homelab watchdog` leaves it stopped. `./homelab start crashy` makes the row plain again (and the app loops again); `./homelab remove crashy --apply`, then `./homelab custom remove crashy --apply`, takes it away. (A wrong `NAVIDROME_MUSIC_PATH` doesn't make a loop: Navidrome mounts the music folder at that path itself.) Tried on Linux with Docker Engine 29.9, Nov 5, 2026.
- `watchdog` lists every check as ✓. A check that fails once only says so; it alerts when it fails twice in a row. The app's Status screen then shows **Watchdog** with all checks passed and when it ran.
- `backup` writes the database dumps and the `.env` copy into `recovery-staging` (Duplicati takes them off-site from 05:00) and ends with a summary.
- `schedule status` shows each job loaded, with a last exit code of 0 once it has run.
- The app's **Backups** screen lists each app's newest copy under *Up to date*, the settings file copied a moment ago, and the Off-site tile naming the place (Proton Drive, the Backup drive); **Back up now** streams the same backup and ends with "Backup done".
- The menu bar's **Back up now** ends with "done" and the time.
- `./homelab digest` prints the same lines as Status › **This week**; `./homelab digest --send` reaches the phone as *Homelab this week*, listing what needs a look (expect the restore test until step 6). From then on it arrives each Sunday morning.
- After logging out and back in, `schedule status` still lists the jobs; the next morning there is a new dump in `recovery-staging/databases` (ISSUE-0005).
- With `HEARTBEAT_URL` set: quit OrbStack, and within 30 minutes healthchecks.io alerts (ISSUE-0006). Start OrbStack again afterwards.

## 5. The proxy and CrowdSec

```sh
./homelab update nginx-proxy-manager
./homelab logs nginx-proxy-manager
./homelab compose crowdsec exec crowdsec cscli bouncers list
```

- `update` rebuilds the proxy image with CrowdSec AppSec; `logs` shows no Lua errors (ISSUE-0001).

## Proven every night

Before a step reaches this page, CI tries it against a real Docker Engine on a Linux runner every night (`.github/workflows/nightly.yml`, the tests in `test/realdocker`), and on each pull request that changes the catalog: ntfy, Vaultwarden, Paperless with its PostgreSQL, and Nginx Proxy Manager installed; `doctor`; the alert token made and a test alert read back; data put into each app through its own API; Duplicati given a backup folder and its jobs (`duplicati destination`, `duplicati setup`), each job read back through Duplicati's API (sources, destination, AES, retention, schedule, the alert URL), then, once the AppData job has run, `restore-test --auto` restoring a sample of settled files and comparing them; Status timed, failing at more than twice the last good run; the nightly backup; the app's page served by `homelab serve` and paired as a phone, with Status, Backups, and **Back up now** clicked through against the real containers; the watchdog bringing back an app that hung and one whose container was removed, with its alert in ntfy; an update and its rollback, across a change of ntfy's database schema (the run starts on ntfy v2.25.0, which refuses the newer ntfy's migrated databases), with ntfy answering on its tokens from before; the same update again with ntfy made to hang before the watchdog saw it well, which the watchdog puts back with its data from before, its tokens checked the same way; then the homelab moved out, wiped, moved in, and the data read back, with ntfy back on the older version it ran, not the newest (the restore drill: timed from the move in to every app answering with its data, written on the run's summary page beside Status's time, and failing at more than twice the last good run and a minute more), and Duplicati's jobs made again on that "new machine" from their existing backups (repaired, then backing up into the same folders). A failed night opens an issue with the run's diagnostics report. Beside it, each night starts a seventh of the rest of the catalog (`TestTheCatalogStarts`, by the day of the week): each app installed alone on a homelab of its own, then its page answering (or, with no page, its container still running a minute on), so every app starts against real Docker at least once a week. An app that needs a setting only the person's own account gives (a tunnel token, a VPN key) is listed as skipped with that reason. Run by hand, the workflow starts all seven shares at once. Beside it, the `rebuild` job (on pull requests that change the real-Docker tests too) is the full rebuild of [Disaster Recovery](<Disaster Recovery.md#scenario-full-mac-rebuild>): Vaultwarden, Paperless with its PostgreSQL, Actual Budget, and Firefly III given data, the nightly backup and every Duplicati job run into a backup folder beside the homelab, the homelab wiped, and `homelab rebuild <that folder>` with the Secrets passphrase bringing it back from the backups alone, each app answering with its data again; its time is on the run's summary page, and a rebuild taking more than twice the last good run's, and a minute more, fails. Beside it, the `domain` job takes `domain setup` through the real proxy and AdGuard Home (Cloudflare left out, as it needs a real account): each proxy host and the rewrite read back, the name resolved through AdGuard, and ntfy answering through the proxy by its name. Beside it, the `wire` job runs `homelab wire` against the real Prowlarr, Sonarr, Radarr, Lidarr, and FlareSolverr, and reads each link back from Prowlarr. Beside it, the `proxy` job builds the homelab's proxy image and runs it with CrowdSec: the bouncer pulling, and a banned address getting 403 until the ban is lifted. Beside it, the `home` job is a new household's first run in Home mode, with a fake tailnet (a Headscale server of the run's own) in place of Tailscale's: Setup's checklist walked as **Do the N I can do for you** walks it (the homelab started, Tailscale installed and signed in, the addresses set up, the alert token, the scheduled jobs installed for real), each step left checked to name the person's part, then that part played (the boxes ticked, a backup folder chosen, the outside check's address filled in) and every step ending done.
